# TeamVibe

현업 팀이 아이디어 대화에서 공동 PRD, 사용자 스토리, 병렬 개발 작업, 통합 테스트로 이어지는 흐름을 함께 관리하는 로컬 해커톤 프로토타입입니다.

처음 받았다면 [처음 실행하기](docs/START_HERE.md)에서 실행 명령, 대표 화면과 검증 자료 위치를 확인하세요. [완료 기준과 근거](docs/ACCEPTANCE.md)는 각 요구사항을 실제 코드·UI·검사 결과에 연결합니다.

## 로컬 제출 묶음

`npm run submission:pack`은 코드·잠금 파일·합성 데이터·문서·시연 화면·보존된 실제 세션 로그를 새 `outputs/submissions/…/TeamVibe.tar.gz`로 만듭니다. macOS/Linux의 `tar` 명령이 필요하며 외부 업로드는 하지 않습니다. 설치된 의존성, 로컬 데이터베이스, 환경변수·키 파일, 생성된 빌드와 이전 압축 파일은 포함하지 않습니다. 기존 압축과 데이터를 덮어쓰거나 삭제하지 않습니다. 최신 경로와 압축 SHA-256은 `outputs/latest-submission.json`에 기록됩니다.

새 폴더에 압축을 푼 뒤 `npm run submission:verify`를 실행하면 `SUBMISSION-MANIFEST.json`의 파일 크기와 SHA-256을 확인합니다. 검사에는 설치된 의존성이 필요 없고 목록 밖 추가 파일은 검사하지 않습니다. 내용 수정 후에는 불일치가 표시되므로 원본 제출 자료와 수정본을 구분할 수 있습니다. 이 결과는 앱 실행 검증을 대신하지 않습니다. 실제 로그는 `evidence/agent-sessions/manifest.json`에 적힌 보존 시점까지 포함합니다.

## 실행

Node.js 22.13 이상과 npm이 필요합니다. 현재 개발·검증 환경은 macOS, Node.js 24.16.0입니다.

```sh
npm ci
npm run db:init
npm run dev
```

터미널에 출력되는 `Local` 주소를 엽니다. 기본 포트는 5173이며 이미 사용 중이면 다음 포트를 선택합니다. 현재 이 작업에서 사용한 주소는 **http://localhost:5174/** 입니다.

첫 실행 때 합성 시연 프로필(김지민·이서연·박현우)과 비품 신청 프로젝트가 생성됩니다. 새 프로젝트와 사용자 데이터를 재실행 시 초기화하지 않습니다. 데이터는 `.wrangler/state/v3/d1`의 로컬 SQLite에 저장됩니다. 이 폴더를 지우면 안 됩니다.

```sh
npm run typecheck
npm run build
npm start
```

`npm run lint`는 별도 선택 검사입니다. 이번 최종 변경에는 추가 lint를 실행하지 않았으며 타입 검사·회귀 검사·빌드 결과를 구분해 기록했습니다.

`npm start`는 빌드된 결과를 로컬 Wrangler로 실행합니다. 기본 주소는 `http://127.0.0.1:8787`이며 `npm start -- --port 8788`로 포트를 지정할 수 있습니다. 빌드가 없으면 먼저 `npm run build`를 실행하라는 안내를 표시합니다. 원격 실행이나 임의 설정 파일 인자는 이 실행기에서 받지 않습니다.

`npm run db:init`과 `npm start`는 사용할 데이터 경로를 출력합니다. 초기화를 생략했거나 스키마가 준비되지 않으면 화면에 `npm run db:init` 안내와 `다시 시도` 버튼이 나타납니다. `/api/health`도 준비되지 않은 데이터베이스에는 503을 반환합니다. 초기화는 아직 적용하지 않은 마이그레이션만 수행하며 반복 실행해도 기존 프로젝트와 수정한 합성 프로필을 초기값으로 덮어쓰지 않습니다.

### 기존 데이터와 분리해서 시연하기

`TEAMVIBE_STATE_PATH`로 로컬 데이터 디렉터리를 선택할 수 있습니다. 상대 경로는 프로젝트 폴더 기준이며 지정하지 않으면 기존 `.wrangler/state`를 사용합니다. 초기화·개발·빌드 결과 실행에 **같은 설정**을 사용해야 합니다. 새 경로를 선택하면 그 경로에서 합성 샘플을 만들며 기존 경로의 데이터는 그대로 남습니다.

```sh
# macOS/Linux 터미널 예시. 이후 명령에도 같은 값을 유지합니다.
export TEAMVIBE_STATE_PATH=".sites-runtime/my-demo-state"
npm run db:init
npm run dev
# 개발 서버를 종료한 뒤 빌드 실행을 확인하려면:
npm run build
npm start -- --port 8788
```

같은 프로젝트 폴더에서 개발 서버를 하나 더 실행하면 기존 서버 주소를 안내합니다. 이 경우 표시된 서버를 사용하세요. 기본 `localhost`가 IPv6에만 연결되는 환경에서 IPv4 주소가 필요하면 `npm run dev -- --hostname 127.0.0.1`을 사용합니다. 데이터 폴더를 삭제하는 방식으로 초기화 오류를 해결하지 마세요.

별도 빈 데이터 경로에서 초기화 안내→마이그레이션→화면 재시도→새 프로젝트 생성→초기화 재실행→개발/빌드 서버 전환의 보존 검사를 수행했습니다(`evidence/fresh-start-validation.json`). 이후 제출 압축을 새로운 폴더에 풀어 기존 node_modules를 복사하지 않고 **npm 캐시만 사용한 새 설치**, 빈 데이터베이스 마이그레이션, 타입 검사·빌드·빌드 서버 대상 전체 테스트를 통과했습니다. 실제 UI 프로젝트 생성과 합성 버튼 실행·검증 기록·완료 처리 후 서버 재시작 보존도 확인했습니다(`evidence/submission-validation.json`). 같은 macOS/Node24.16 환경에서 수행했으며 캐시 없는 레지스트리 다운로드나 별도 컴퓨터·다른 운영체제 설치는 미검증입니다.

최신 자동 갱신 수정이 포함된 압축에서도 캐시 기반 새 설치·빌드·전체 회귀 검사와 **프로젝트 생성부터 두 프로필 참여·대화·PRD 동의·스토리 반입·병렬 작업·통합·실제 실행·완료까지 UI 흐름**을 확인했습니다. 서버 재시작 후 전체 프로젝트가 같고 코드가 다시 실행되는 것도 확인했습니다(`evidence/submission-refresh-validation.json`). 첫 빌드 서버 검사에서는 실행기 재시작503이 발생했고 같은 서버에서 전체 재검사는 통과했습니다. 원래 실패 로그도 보존했습니다.

## 시연 순서

왼쪽 프로젝트 이름을 누르면 이름·설명 검색이 열립니다. `참여 중`과 `휴지통`을 나누어 보여주며, 같은 이름의 프로젝트는 설명·오너·팀원 수로 구분할 수 있습니다. 검색어는 보관 상태를 전환해도 유지되고, Enter로 선택하거나 Escape로 취소할 수 있습니다. 휴지통 프로젝트를 열면 이름을 확인한 뒤 오너가 복원합니다. 선택 창을 다시 열면 검색어는 초기화됩니다. 현재 프로필이 참여한 프로젝트만 대상으로 하며, 목록 전체를 로컬 브라우저에 불러와 검색합니다.

1. 김지민 프로필을 선택하고 `만들기`에서 새 프로젝트의 문제와 목표를 입력합니다.
2. `팀 관리`의 초대 코드를 복사합니다. 다른 브라우저 프로필이나 시크릿 창에서 이서연/박현우를 선택하고 `참여하기`에 입력합니다. 같은 브라우저의 탭은 로그인 쿠키를 공유합니다.
3. 각 사용자가 `아이디어 대화`를 만들고 업무 문제를 입력합니다. 대화 원문 옆 `요구사항으로 정리`로 요구사항을 등록합니다.
4. 필요할 때 `ChatGPT 대화 묶음 복사`로 프롬프트를 얻고 사용자가 직접 ChatGPT에서 대화합니다. 응답은 `ChatGPT 응답 가져오기`에 붙여넣습니다. 앱이 자동으로 ChatGPT에 접속하거나 내용을 전송하지 않습니다.
5. `공동 PRD → ChatGPT로 요구사항 정리`에서 팀 대화 묶음을 만들고, 직접 전달한 응답 JSON을 원문과 비교해 반입할 수 있습니다. `요구사항`에서 중복을 편집·통합하거나 휴지통으로 옮기고 충돌의 결정 근거를 남깁니다. 검토 후 요구사항을 합의됨으로 바꿉니다. `요구사항으로 초안 만들기`로 문서를 묶고 필요하면 편집합니다.
6. 팀원 각각이 PRD에 동의합니다. `스토리 보드 → ChatGPT로 스토리 설계`에서 요청을 직접 전달하고 응답 JSON을 검토·등록합니다. `PRD로 분할 초안`의 규칙 초안도 사용할 수 있습니다. 완료 조건·테스트·의존성을 검토하고 `개발 준비`로 저장합니다.
7. 독립 스토리 여러 개를 선택해 `선택 스토리 병렬 시작`을 누릅니다. `개발 작업` 탭에서 작업마다 프롬프트를 복사하여 별개의 ChatGPT 작업으로 전달합니다.
8. 완료한 결과 JSON을 각 작업의 `결과 가져오기`로 등록합니다. `선택 작업 통합`에서 시작 코드·현재 릴리스·제출 파일을 비교합니다. 충돌이 있으면 최종 코드와 해결 근거를 입력하거나 제출 결과를 수정합니다.
9. 제출한 작업을 선택해 통합하면 `테스트 랩`에서 실제 HTML/CSS/JavaScript를 실행할 수 있습니다. 외부 통신과 앱 데이터 접근을 제한한 iframe입니다.
10. 실제 수행한 테스트의 절차·기대·결과를 기록합니다. 피드백은 후속 스토리로 전환합니다. `활동 기록 → 제출 자료`에서 코드와 작업·검증 이력을 JSON으로 내려받습니다.

상단 단계 버튼은 각각 아이디어 대화, 공동 문서, 스토리 보드, 개발 작업, 실행 미리보기로 이동합니다. 독립 스토리를 시작하면 개발 작업 목록이 열리고, 통합하면 테스트 미리보기가 열립니다. `개발 작업`의 숫자는 휴지통을 제외한 전체 작업 수이며 목록 위에 결과 대기·통합 대기·통합 완료·취소를 나누어 표시합니다. 결과 대기는 사용자가 ChatGPT에 직접 전달하고 반입할 차례라는 뜻입니다.

개요의 다음 작업은 현재 PRD 합의, 이전 기준의 대기 작업, 제출·진행 작업, 테스트와 열린 피드백을 보고 안내합니다. 예전 릴리스가 있어도 PRD 동의가 철회되면 문서 검토가 먼저 표시됩니다. 이 안내는 이동을 돕는 정보이며 API의 합의·의존성·검증 조건이나 사용자의 완료 판단을 대신하지 않습니다.

`공동 PRD → 버전 기록`에서 각 본문의 작성자·작성 시각·작성 경위와 요구사항 반영 기준을 확인합니다. 이전 본문의 작성 정보와 이를 보관하고 다음 버전을 만든 사람을 구분합니다. 직접 편집, 규칙 초안 생성, 이전 본문 복원도 구분하며 도입 전 작성 정보를 추정하지 않습니다. 같은 내용을 그대로 저장하면 기존 작성 정보와 동의를 유지합니다.

`vN 본문으로 새 버전 만들기`는 서버에 보존된 해당 본문으로 새 PRD를 만들고 복원 출처 버전을 남깁니다. 현재 본문과 같더라도 명시적인 복원은 새 버전을 만듭니다. 이전 본문과 이력은 그대로 남고, 현재 요구사항 반영 기준으로 기록되므로 내용을 다시 비교·검토하고 팀원들이 재동의해야 합니다. 본문이 실제 요구사항을 충족하는지는 자동으로 판단하지 않습니다. 빈 초기 문서는 복원할 수 없습니다.

PRD가 비어 있거나, 요구사항·목표 변경을 아직 반영하지 않았거나, 미해결 요구사항이 있으면 동의 버튼 아래에 이유와 해당 요구사항 이름을 표시합니다. `미해결 요구사항 검토`로 바로 이동할 수 있습니다. 현재 문서에 이미 동의한 사람은 동의를 철회할 수 있습니다.

요구사항의 내용·상태·결정·출처 버전이 그대로인 저장과, 내용·반영 기준이 그대로인 PRD 저장은 기존 동의와 완료 근거를 유지합니다. 동일한 출처들의 표시 순서만 바꾸어도 동의를 해제하지 않습니다. 실제 요구사항이나 출처 버전이 바뀌면 기존처럼 재검토가 필요합니다. 문구가 같아도 변경된 요구사항을 명시적으로 검토해 PRD를 저장하면 새 반영 기준의 버전으로 기록합니다. 저장 요청 자체는 프로젝트 활동과 동시 편집 버전에 계속 남습니다.

스토리의 `개발 준비` 상태와 `현재 시작 가능`은 다릅니다. PRD 합의·스토리 버전·선행 작업의 현재 릴리스 검증·중복 작업을 함께 확인한 뒤 시작할 수 있습니다. 시작할 수 없는 카드에는 이유와 선행 스토리 이름을 표시합니다. 선택한 후 팀의 변경이나 검증 기록 삭제로 조건이 달라지면 선택을 유지한 채 시작을 막고, `시작할 수 없는 선택 해제`로 해당 선택만 뺄 수 있습니다. 한 번에 최대 10개를 시작합니다. 삭제한 검증 기록을 복원하더라도 선행 스토리의 완료 처리는 다시 확인해야 합니다.

`테스트 랩 → 실행 미리보기` 아래에서 스크립트·처리되지 않은 비동기 오류, 파일 로드 실패, 격리 정책으로 차단된 요청을 확인할 수 있습니다. 현재 실행의 처음 20건만 표시하며 `오류 내용 복사`에 릴리스 이름·ID를 포함합니다. 사용자가 직접 ChatGPT에 전달할 수 있고 자동 전송은 없습니다. 새로운 오류가 생기면 이전 복사 완료 안내를 지웁니다. 복사에 실패하면 화면의 오류 문구를 직접 선택할 수 있습니다.

### 팀 대화에서 요구사항 제안 반입

`공동 PRD → ChatGPT로 요구사항 정리`의 `최신 요구사항 정리 요청 만들기`는 팀의 사용자 메시지·수동 ChatGPT 응답과 기존 요구사항을 묶습니다. 요청 원문을 직접 선택하거나 복사해서 ChatGPT에 전달합니다. 로컬 도우미와 휴지통 메시지·대화는 제외합니다. 응답 JSON을 붙여넣거나 파일로 불러온 뒤 `내용 검토`에서 제목·우선순위·미결정 사항·원문 출처를 확인하고 명시적으로 등록합니다. 검토 화면에 불러오기만 하면 서버 데이터는 바뀌지 않습니다.

JSON은 `batchId`, `projectId`, `projectVersion`, `source`, `requirements`를 포함합니다. 각 제안에는 `key`, `title`, `description`, `priority`, `status`, `reviewNote`, `sourceRefs`가 필요하며, 출처는 `{messageId, revision}` 목록입니다. 한 묶음은 1~20개이며 상태는 `proposed` 또는 `conflict`만 허용합니다. 충돌에는 `reviewNote`가 필수입니다. 합의됨으로 자동 반입하지 않으며 기존 요구사항이나 PRD 원문을 덮어쓰지 않습니다. 등록하면 PRD 동의를 해제하고 문서 재검토를 요구합니다.

다른 프로젝트, 이미 반입한 묶음, 요청 이후 변경된 프로젝트, 삭제·수정된 출처는 반입을 막습니다. 팀의 변경이 있으면 최신 요청과 응답으로 다시 검토합니다. 등록 후 편집·휴지통·복원을 사용하며, 원문 버전과 반입 출처·당시 검토할 점은 보존됩니다. 같은 묶음을 재반입하는 대신 기존 항목을 수정하거나 복원하세요. 내용의 타당성·중복·충돌 해소는 사람이 판단합니다.

`data/sample-requirement-plan.json`은 **팀 대화에서 요구사항 · 합성 반입**에 실제 반입한 합성 응답입니다. 실제 ChatGPT가 생성한 응답이 아니며 재반입은 중복으로 차단됩니다. JSON은 200,000자, 파일은 800 KB, 요청 묶음은 400,000자 제한입니다. 요청이 너무 길면 기존 대화별 작업 묶음과 개별 요구사항 등록을 사용합니다.

## 결과 JSON 형식

### 사용자 스토리 설계

`ChatGPT로 스토리 설계`에서 복사한 요청에는 공동 PRD, 요구사항 ID, 기존 스토리와 반환 형식이 포함됩니다. 응답 JSON을 붙여넣거나 파일로 불러온 뒤 `내용 검토`에서 각 완료 조건·테스트·선행 관계를 읽고 백로그로 등록합니다. 자동으로 개발을 시작하지 않습니다. 복사가 지원되지 않으면 `설계 요청 내용 보기`에서 직접 선택할 수 있습니다.

설계는 `planId`, `projectId`, `prdRevision`, `source`, `stories`로 구성됩니다. 스토리마다 `key`, `title`, `description`, `acceptance`, `tests`, `dependencies`, `existingDependencies`, `requirementIds`, `ownerId`를 사용합니다. `dependencies`는 같은 묶음의 key, `existingDependencies`는 기존 스토리 ID입니다. 현재 요구사항이 있으면 각 스토리는 최소 하나에 연결해야 합니다. 담당자를 지정하지 않으면 빈 문자열로 둡니다.

한 묶음에 1~20개를 반입합니다. 같은 묶음 ID 재사용, 잘못된 참조, 순환 의존성, 다른 프로젝트, 오래된 PRD는 저장을 거절합니다. 검토 중 팀 변경이 있으면 다시 검토해야 합니다. 모두 통과한 경우에만 한 번에 저장하며, 반입 출처는 스토리 수정·휴지통·복원 후에도 남습니다. 서로 다른 묶음 ID로 제출한 의미상 중복은 팀이 검토해야 합니다.

스토리 편집의 `먼저 완료할 스토리`와 `연결 요구사항`은 이름·상태를 보고 여러 항목을 선택합니다. ID를 직접 입력할 필요가 없습니다. 선행 스토리를 선택하면 그 작업의 통합·검증이 끝나야 개발을 시작할 수 있습니다. 편집 중 선택 후보가 휴지통으로 이동하면 해당 연결을 해제하도록 안내하며 입력을 숨기지 않습니다.

`data/sample-story-plan.json`은 **ChatGPT 스토리 설계 · 합성 시연** 프로젝트에 실제로 반입한 합성 예제입니다. 이미 반입했으므로 같은 파일을 다시 등록하면 중복 안내가 나옵니다. 새 프로젝트에서는 그 프로젝트에서 복사한 ID와 최신 PRD 버전으로 설계를 작성해야 합니다. 실제 ChatGPT에서 생성한 응답으로 표시하지 않습니다.

### 개발 결과

새 개발 작업의 응답에는 개발 요청에서 받은 `context`가 필수입니다. 아래 식별 값은 예시이며 해당 작업의 요청 값을 그대로 사용하세요. 프로젝트·개발 작업·스토리·스토리 버전·PRD 버전·시작 릴리스가 일치해야 반입됩니다. 취소 후 같은 스토리를 다시 시작해도 개발 작업 ID가 달라 이전 응답을 재사용할 수 없습니다.

```json
{
  "context": {
    "projectId": "개발 요청의 프로젝트 ID",
    "runId": "개발 요청의 작업 ID",
    "storyId": "개발 요청의 스토리 ID",
    "storyRevision": 1,
    "prdRevision": 1,
    "baseReleaseId": ""
  },
  "files": {
    "index.html": "<!doctype html><html><body><h1>샘플</h1><script src=\"app.js\"></script></body></html>",
    "app.js": "document.body.dataset.loaded = 'yes';"
  },
  "deletedFiles": [],
  "log": "실제로 수행한 구현과 테스트, 검증하지 않은 부분을 기록합니다.",
  "source": "ChatGPT 세션 제목 또는 로컬 에이전트 로그 파일명"
}
```

`context`의 버전과 시작 릴리스도 실제 요청 값과 같아야 합니다. 빈 시작 릴리스는 새 앱을 뜻합니다. 반입 문서에는 `context`, `files`, `deletedFiles`, `log`, `source`만 허용하며, `id`나 `type`으로 화면에서 선택한 작업을 바꿀 수 없습니다. 입력 오류가 나도 붙여 넣은 내용은 남습니다. 저장한 결과를 수정할 때도 같은 작업 정보가 유지됩니다.

결과 JSON 파일은 1.2 MB까지 읽습니다. 파일을 읽는 동안 편집·저장·닫기를 잠그고 진행 상태를 표시합니다. 파일 읽기 실패, JSON 형식 오류, 용량 초과를 구분해 안내하며 기존 입력은 유지합니다. 같은 파일을 다시 선택할 수도 있습니다. 양식을 새로 열거나 새 입력이 생긴 뒤에는 이전 파일 읽기 결과로 덮어쓰지 않습니다. 파일을 읽어 양식에 채우는 것과 프로젝트에 저장하는 것은 별도 단계이며, 저장할 때 작업 context와 코드 형식 검사를 다시 받습니다.

`개발 작업 → 결과 수정 이력`에서 변경 전 파일·제외 요청·수행 로그·출처와 반입자를 볼 수 있습니다. 실제 값이 바뀔 때만 새 결과 버전을 기록하며 같은 결과를 다시 저장하거나 파일 목록의 순서만 바꾸면 기존 반입 정보와 이력을 유지합니다. 반입자는 결과를 저장한 팀원이며 AI·코드 작성자나 테스트 수행자를 뜻하지 않습니다. 도입 전 반입자·시각·변경 이력은 추정하지 않습니다.

이전 결과의 `vN 결과 JSON 보기`를 열어 내용을 복사하고, 같은 작업의 `제출 결과 수정`에서 다시 반입하면 새 결과 버전으로 저장됩니다. 원래 개발 요청·작업 문맥은 바뀌지 않습니다. 이전 JSON에 없는 파일은 시작 코드 기준의 기존 반입 규칙을 따르므로, 최종 통합 내용을 다시 확인해야 합니다. 통합·취소된 작업은 결과를 수정할 수 없고 이력은 계속 읽을 수 있습니다. 취소 작업을 휴지통으로 옮기거나 복원해도 이력은 남습니다.

반입 당시 로그는 원문 그대로 보존합니다. 그 뒤 실제 실행한 내용은 테스트 랩의 검증 기록에 남기세요. 이력은 전체 결과 스냅샷을 저장하므로 수정 횟수와 코드 크기에 따라 프로젝트 데이터가 커집니다. 대규모 파일·장기 보관 성능은 검증하지 않았습니다.

이 기능 도입 전의 작업은 context 없는 기존 응답을 받을 수 있고 양식에 한계를 표시합니다. 이 경우 내용과 선택한 작업을 직접 확인해야 합니다. 이전 작업도 context를 포함했다면 일치 여부를 검사합니다. 문맥 일치는 전달 오류를 막는 기준이며 코드의 기능적 타당성은 통합 후 실제 테스트로 확인해야 합니다.

- 추가·수정·제외 경로를 합해 1~30개, 개별 코드 300,000자, 전체 코드 800,000자 이내입니다. 통합 릴리스도 파일 30개·코드 800,000자 이내입니다.
- `deletedFiles`는 선택 필드이며, 개발 시작 릴리스에 있던 파일의 상대 경로 배열입니다. `files: {}`와 제외 목록만 제출할 수도 있습니다. 같은 경로를 수정과 제외에 동시에 넣거나 `index.html`을 제외할 수 없습니다.
- 허용 확장자: html/css/js/json/txt/svg. 경로 이탈과 절대 경로는 차단합니다.
- `index.html`에서 상대 경로로 참조하는 CSS 및 classic JS를 인라인으로 묶습니다.
- CDN, 외부 API, fetch, 서버 프로세스, 모듈 import, 일반 파일 시스템, 앱의 쿠키·로컬 저장소를 사용할 수 없습니다.
- 미리보기 재실행 시 만들어진 샘플 앱의 메모리 상태는 초기화됩니다. TeamVibe 프로젝트 데이터는 DB에 남습니다.
- 새 context 형식의 실제 반입 예제는 `data/sample-run-result-app.json`, `data/sample-run-result-style.json`입니다. **병렬 결과 반입 · 작업 일치 확인**에 이미 반입·통합한 응답으로 다른 작업에서 재사용할 수 없습니다. `data/sample-artifact-app.json`, `data/sample-artifact-style.json`은 도입 이전의 합성 예제입니다. 새 작업에서는 새 개발 요청의 context를 포함해야 합니다. 모두 실제 ChatGPT 실행 결과가 아닙니다.
- `data/sample-artifact-removal.json`은 기존 `legacy.js`와 HTML 참조를 함께 제외하는 합성 예제입니다. 이 파일이 시작 코드에 있는 작업에만 적용됩니다.

## 검증

서버 실행 후:

```sh
TEAMVIBE_URL=http://localhost:5174 npm test
```

검증은 매번 별도의 합성 프로젝트를 만듭니다. 기존 프로젝트는 수정·삭제하지 않습니다. API 검증이 코드의 브라우저 동작까지 입증하는 것은 아닙니다. 실제 수행 범위와 발견·수정 내역은 `evidence/VERIFICATION.md`를 확인하세요.

원본 Codex 세션은 `evidence/agent-sessions`에 스냅샷과 해시를 보존합니다. `node scripts/preserve-session.mjs`는 이 작업의 실제 원본 로그에서 갱신하며, 다른 컴퓨터에서는 원본 위치가 없으므로 실행되지 않을 수 있습니다. 앱 활동 기록·합성 샘플·실제 에이전트 로그는 서로 구분합니다. 외부 업로드는 하지 않았습니다.

## 현재 한계

- 로컬 데모 프로필을 자유롭게 선택하는 방식입니다. 실제 인증/비밀번호/SSO가 없으므로 운영 데이터나 민감한 정보를 사용하면 안 됩니다.
- 기본 서버는 로컬에서만 동작하며 API는 localhost 출처를 제한합니다. 다른 컴퓨터의 팀원 접속은 현재 지원하지 않습니다. 별도 브라우저 세션으로 팀을 시연합니다.
- 프로젝트 단위 JSON을 SQLite에 저장합니다. 버전 충돌 시 저장을 거절하고, 편집 양식에서 원본·내 입력·팀의 최신 값을 비교해 사용자가 합칠 내용을 선택합니다. 긴 문서나 코드 JSON 안의 변경은 필드 전체를 비교합니다. 대규모 팀/장기 운영을 위한 정규화·첨부파일 저장은 후속 과제입니다.
- ChatGPT로의 실제 전송과 응답 수신은 사용자 수동 작업입니다. 이번 검증에서는 외부 ChatGPT 전송 없이 로컬 합성 결과로 반입·통합을 확인했습니다.
- 테스트 결과 기록은 사용자 진술입니다. 코드의 보안·정확성이나 모든 완료 조건을 자동 보증하지 않습니다.
- 브라우저 샌드박스는 완전한 악성 코드 실행 환경이 아닙니다. 신뢰할 수 있는 합성 시연 코드만 사용하세요.
- 시연 앱은 HTML/CSS/classic JS만 지원합니다. 실제 백엔드, 데이터베이스를 요구하는 산출물은 별도 로컬 개발 환경이 필요합니다.


스토리의 내용·완료 조건·테스트 기준·연결 집합·PRD 기준이나 준비 상태를 실제로 바꾸면 새 버전이 됩니다. 같은 값을 저장하거나 선행/요구사항 연결의 표시 순서만 바꿀 때는 버전을 유지합니다. 테스트 순서 변경은 기준 키가 달라지므로 새 버전이 됩니다. 검토·완료 스토리를 열면 `현재 상태 유지`가 기본 선택되며, 그대로 저장하면 진행 상태와 기존 검증 근거를 유지합니다. 그 선택에서 실제 내용을 바꾸면 백로그로 돌아가고, 명시적으로 `개발 준비`를 선택하면 새 버전 개발을 준비합니다. 진행 중인 개발 작업의 내용은 먼저 작업을 취소해야 수정할 수 있습니다.

스토리 카드의 담당자 버튼에서는 개발 중에도 담당자를 바꾸거나 `미지정`으로 해제할 수 있습니다. 담당만 바뀌면 스토리 버전·진행 상태·원래 개발 요청·제출 결과·검증 기록을 유지합니다. 일반 스토리 편집에서도 담당자만 바꾸면 같은 규칙을 적용합니다. 담당 변경 이력에는 이전/새 담당자, 변경자와 시각이 남으며 팀원 제외·탈퇴에 따른 해제도 구분합니다. 기록이 없던 과거 변경은 추정해서 만들지 않습니다. 동시에 담당자가 바뀌면 최신 값과 내 입력을 비교해 선택해야 하며, 현재 팀원이 아닌 사람에게는 배정할 수 없습니다.

팀원 제외는 해당 사람의 PRD 동의만 해제합니다. 자발적인 팀 탈퇴는 기존 정책에 따라 전체 PRD 동의를 해제하므로 완료 스토리는 검토 대기로 돌아갈 수 있습니다. 이 경우에도 스토리 버전과 구현·테스트 원본은 유지되며, 남은 팀이 다시 동의하고 완료 근거를 확인해야 합니다.

`담당자 인계 · 진행 작업과 검증 보존` 합성 프로젝트에서 실제 버튼 실행·테스트 기록·완료 후 담당 변경, 팀원 제외, 동시 수정 비교 및 인계 후 재실행을 확인했습니다. 스토리2개의 v1과 완료/개발 중 상태, 원래 코드·프롬프트·검증 기록이 유지됩니다. `evidence/story-assignment-validation.json`, `story-assignment-browser-result.json`, `story-assignment-server-result.json`과 `evidence/screenshots/story-assignment-mobile-conflict.png`에 범위와 실제 결과가 있습니다.

개발 작업은 시작 당시의 PRD·스토리 버전에 연결됩니다. `개발 요청과 시작 코드 보기`에는 당시 완료 조건과 테스트 기준이 남고, 검증 기록에는 당시 기준 문구가 보존됩니다. 이전 버전의 코드와 테스트 기록으로 수정한 스토리를 완료할 수 없습니다. 예전 릴리스로 되돌리면 최신 스토리의 완료 근거도 다시 확인합니다. 저장 요청의 활동 기록과 프로젝트 동시 편집용 버전은 내용이 같아도 증가합니다.

## 자동 갱신과 저장된 내용 보존

프로젝트 목록과 팀의 변경은 5초 간격으로 갱신합니다. 쓰기 작업 전후에 시작된 오래된 읽기 응답은 반영하지 않고, 같은 프로필에서 이미 받은 프로젝트 버전보다 낮은 응답으로 화면을 되돌리지 않습니다. 오래 걸리는 갱신은 15초에 중단하고 다음 주기에 재시도합니다. 작성 중인 양식은 자동으로 덮어쓰지 않으며 저장 시 버전 충돌을 비교합니다. 멤버십 목록에서 빠진 프로젝트를 이전 데이터로 다시 표시하지 않습니다.

실제 로컬 브라우저에서 저장 뒤 옛 응답이 도착하는 오류를 재현한 뒤 수정·재검증했고, 응답 시간 초과 후 새 변경을 받는 것까지 확인했습니다(`evidence/workspace-refresh-validation.json`). 서로 다른 탭은 로그인 쿠키를 공유하므로 사용자별 동시 시연에는 별도 브라우저 프로필을 사용하세요.

## 동시 편집 충돌 해결

`선택 작업 통합`의 릴리스 이름·최종 코드·파일 제외 선택·해결 근거·ChatGPT 요청과 응답은 현재 페이지에서 사용자·프로젝트·선택 작업 묶음별로 보존합니다. 창을 닫고 화면을 이동하거나 다른 작업들을 검토한 뒤 같은 작업들을 다시 선택하면 입력이 돌아옵니다. 선택 순서는 달라도 같은 묶음으로 취급합니다. 검토 당시 프로젝트 버전도 유지하므로 팀의 변경이 있으면 입력을 보존한 채 통합을 차단하고 명시적인 재검토를 요구합니다. 보존된 해결안 JSON도 최신 프로젝트·작업·릴리스 기준 검사를 다시 받습니다.

`통합 입력 초기화`는 확인 후 현재 묶음의 작성 자료만 비우며 제출 원본과 기존 릴리스는 유지합니다. 성공한 통합은 제출했던 초안만 정리합니다. 초안은 페이지 메모리에만 있으므로 **새로고침·탭 종료 후에는 복구되지 않습니다**. 이미 통합되거나 취소된 작업은 기존과 같이 다시 통합할 수 없습니다.

### 개발 코드 통합

새 개발 작업의 요청 문서에는 시작 당시 활성 릴리스의 코드가 포함됩니다. 작업이 시작된 뒤 다른 릴리스가 활성화되어도 기준 코드와 요청 문서는 바뀌지 않습니다. `개발 요청과 시작 코드 보기`에서 직접 확인할 수 있습니다.

반입 시 `files`에는 추가·수정한 파일의 전체 내용을 넣습니다. 생략한 파일은 보존하고, 제외할 경로만 `deletedFiles`에 명시합니다. 바꾸지 않은 기준 파일을 함께 반환해도 팀원의 최신 변경이나 이미 제외한 파일을 되돌리지 않습니다. 같은 파일을 서로 다르게 바꿨거나 한쪽에서 제외를 요청했다면 통합 화면에서 시작·현재·제출 코드를 비교합니다. 사용할 내용 또는 파일 제외를 선택하고, 유지한 변경과 다시 검증할 내용을 해결 근거에 적습니다. 검토 중 프로젝트가 바뀌면 입력을 보존하고 재검토를 요구합니다.

통합 결과는 새 릴리스이며 원래 제출 파일과 이전 릴리스는 보존합니다. `테스트 랩 → 릴리스 이력`에서 제외한 파일·해결 근거·작성자를 읽고 이전 릴리스를 활성화하여 원래 코드를 복원할 수 있습니다. 기준이 기록되지 않은 예전 작업은 현재 파일과 다른 내용을 덮어쓸 때 직접 검토해야 하며 파일 제외 요청은 최신 릴리스에서 시작한 새 작업을 사용합니다. 코드 의미나 파일 참조를 자동으로 분석·검증하지 않으므로 제외한 파일의 참조도 함께 수정하고 실제 동작을 테스트해야 합니다.

코드를 직접 합치기 어려우면 `ChatGPT와 충돌 해결하기 · 수동 전달`을 펼칩니다. PRD·작업·테스트 기준·시작/현재/제출 코드를 담은 요청을 직접 복사해 전달하고, 응답 JSON을 붙여넣거나 파일로 가져옵니다. `해결안을 검토 양식에 채우기`는 저장이나 통합 없이 초안만 채웁니다. 팀이 근거와 코드를 수정·검토한 뒤 `검토한 코드로 통합`을 눌러야 새 릴리스가 생깁니다.

해결안은 `projectId`, `projectVersion`, `activeReleaseId`, `runIds`, `source`, `resolutions`를 포함합니다. `resolutions`는 충돌 파일 경로별 `{ "content": "전체 코드", "reason": "유지한 변경과 재검증 사항" }`입니다. 파일 제외를 선택하면 `content`에 JSON `null`을 넣습니다. 빈 문자열은 빈 파일이며 삭제와 다릅니다. 요청에 지정된 프로젝트·버전·릴리스·작업과 정확히 일치해야 하며, 충돌 파일만 모두 포함해야 합니다. 프로젝트가 변경됐으면 최신 요청으로 다시 검토합니다. 반입 출처와 최종 검토 근거는 릴리스에 남습니다. `data/sample-resolution-plan.json`은 **ChatGPT 충돌 해결안 · 합성 반입** 프로젝트에서 사용한 합성 응답이며 실제 ChatGPT가 생성한 결과가 아닙니다. 이미 통합된 예제여서 재사용하려면 새로운 충돌 상황의 요청이 필요합니다.

### 공동 편집 양식

같은 프로젝트에서 다른 팀원이 먼저 저장하면 작성 중인 입력을 유지한 채 비교 화면을 엽니다. 서로 다른 필드를 수정한 경우 양쪽 변경을 보존하며, 같은 필드를 서로 다르게 수정했다면 `내 입력 사용` 또는 `팀의 최신 값 사용`을 선택합니다. `변경을 합쳐 저장 준비`로 양식에 반영한 뒤 내용을 더 편집하거나 저장할 수 있습니다. 비교하는 사이 다른 변경이 발생하면 다시 충돌을 확인합니다.

편집 대상이 휴지통으로 이동하면 재저장을 막고 입력 복사·취소를 제공합니다. 요구사항 내용만 편집할 때는 다른 팀원이 추가한 대화 출처도 보존합니다. 두 시연 프로필의 실제 API 저장과 브라우저 편집을 조합한 확인 결과는 `evidence/edit-conflict-browser-result.json`에 있습니다.

실행 HTML만 따로 확인하려면 프로젝트 폴더에서 아래처럼 로컬 서버를 열고 `http://127.0.0.1:8086/safe-edit-preview.html`에 접속합니다. 포트가 사용 중이면 다른 포트를 선택하세요. 이 합성 앱의 신청은 실행 중 메모리에만 남고 새로고침하면 초기화됩니다. `file://` 직접 열기는 검증하지 않았습니다.

```sh
python3 -m http.server 8086 --bind 127.0.0.1 --directory evidence
```
